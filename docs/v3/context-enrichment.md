# CloudWatch incident context enrichment

V3.18 collects bounded, read-only operational context for AWS alarm incidents before the
shared triage pipeline runs. Telemetry is evidence, not authority: tenant scope comes from
the claimed Job, persisted Incident, V3.17 alert receipt, persisted AWS integration, worker
authorization, and PostgreSQL RLS. AWS response fields never select an organization,
workspace, integration, account, or region.

```text
TRIAGE worker
  -> load Incident/TriageRun and persisted alert receipt
  -> resolve READY AwsIntegration under RLS
  -> reuse V3.16 STS AssumeRole boundary and validate caller account/role
  -> DescribeAlarms for the one persisted alarm name
  -> GetMetricData for one validated alarm metric
  -> FilterLogEvents for configured exact log groups
  -> redact, normalize, and apply hard budgets
  -> persist immutable ContextSnapshot and items
  -> project bounded context into the shared triage input
  -> retrieve workspace knowledge independently
  -> run shared triage and persist result/evidence
```

## Eligibility and binding

Enrichment runs only in the hosted TRIAGE worker for an `aws.cloudwatch` alarm incident.
The integration must be READY, enabled, linked by the accepted V3.17 receipt, configured
for the incident region, and verified for each collector capability. Manual and non-AWS
incidents continue without AWS enrichment. Browser/history requests and alert-ingestion
requests never collect telemetry.

The worker assumes only the configured role with the persisted ExternalId for a bounded
session. It validates the returned account and assumed-role identity. Credentials remain
inside the short-lived adapter, are neither persisted nor logged, and are discarded with
the execution object.

## Collection policy

Policy is deployment configuration, never incident or browser input. Initial defaults are:

- metrics and logs: 15-minute lookback from the alarm observation time;
- forward window: 2 minutes;
- metric points: 120;
- log events: 100;
- log bytes: 65,536;
- provider calls: 8;
- total normalized context: 80,000 characters;
- individual log message: 4,000 characters;
- exact configured log groups: at most 20.

Metric collection uses `DescribeAlarms` for the known alarm and `GetMetricData` for a
validated single metric. It does not use account-wide `ListMetrics` discovery. Direct
single-metric alarms are supported. Metric math, search expressions, and composite alarms
degrade explicitly as unsupported rather than executing provider expressions.

Log collection uses `FilterLogEvents` only for exact integration-configured log group names,
the configured incident region, and the bounded incident window. It stops on result, byte,
pagination, or provider-call budgets. No log configuration means `not_configured`; AIRA does
not guess groups from alarm names or enumerate the account. Filters and provider queries are
deterministic application logic and are never supplied by users or generated by an LLM.

## Redaction and context budget

Raw SDK envelopes are not persisted or sent to the model. Structured JSON keys such as
password, secret, token, authorization, cookie, API key, access key, and session are redacted
first. Text patterns then redact bearer/authorization values, common secret assignments, AWS
access-key-like values, and private-key blocks. Nesting, item count, message size, bytes,
datapoints, provider calls, and total context are bounded before persistence or model use.
This is bounded application-layer redaction, not a claim of complete enterprise DLP.

Selection is deterministic: the alarm metric is first, log groups follow configured order,
and normalized events are ordered by proximity to the collection window. Truncation is
recorded on items and the snapshot. The LLM cannot select AWS APIs or expand collection.

## Persistence, retries, and evidence

Each TriageRun has at most one immutable `incident_context_snapshot` with ordered context
items. The snapshot records integration, provider, region, collection window, policy version,
collector diagnostics, completeness, and truncation. A valid snapshot is reused by retries;
a distinct operator re-triage receives a new TriageRun and snapshot. Snapshot insertion
revalidates the active Job claim token while holding the Job row lock, so a stale worker
cannot overwrite or duplicate context.

Snapshot and item tables carry organization/workspace scope, tenant-consistent foreign keys,
and forced RLS. Historical APIs expose only normalized, redacted context. Operational items
also produce explicit `operational` evidence provenance. They are incident-specific records:
they are never document versions, knowledge sources, FAISS inputs, or automatically added to
the persistent workspace corpus.

Metrics and Logs are optional collectors. One may fail while triage continues with the other
and workspace knowledge; the snapshot is marked partial with safe diagnostics. Missing or
disabled integration, unconfigured region, invalid binding, and identity mismatch are
deterministic failures. Throttling and transient network failures during mandatory role
assumption use the V3.10 transient retry category. Cancellation is checked before role
assumption, between collectors, before LLM triage, and before result commit. SDK calls retain
bounded connect/read timeout behavior; immediate interruption of an in-flight call is not
claimed.

Audit records mark enrichment start, completion, and partial completion without raw logs,
metric arrays, queries, or credentials. Observer hooks use low-cardinality outcomes; tenant,
integration, incident, alarm, and log-group identifiers are not metric dimensions.

## Boundaries and deferred work

V3.18 creates no AWS resources and makes no AWS mutations. V3.19 owns action records, not
context collection. V3.22 owns production IAM, ECS, network, and provider infrastructure.
Retention cleanup remains a V3.25 policy concern; V3.18 keeps snapshots needed to explain
historical triage. No live customer AWS infrastructure is claimed as tested by this phase.
