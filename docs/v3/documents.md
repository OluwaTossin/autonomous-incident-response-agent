# Version 3 Hosted Documents

V3.7 stores hosted source-document bytes in private S3-compatible object storage and
authoritative metadata in PostgreSQL. It does not connect documents to FAISS or publish
knowledge indexes; V3.8 and V3.9 own those flows.

## Hosted And Self-Hosted Storage

| Concern | Version 2 self-hosted | Version 3 hosted |
|---|---|---|
| Upload | FastAPI streams to a workspace directory | Client uploads through a short-lived presigned PUT |
| Content | `workspaces/<id>/data/<category>/<filename>` | Private immutable object |
| Metadata | Filesystem path and stat | PostgreSQL document/version rows |
| Tenant scope | Process-selected `WORKSPACE_ID` | Authorized organization/workspace context plus RLS |
| Index input | Existing corpus globs | Deferred to V3.8 |

The Version 2 `/admin/upload`, file suffix checks, workspace paths, local FAISS input,
CLI, and Compose behavior are unchanged. The hosted S3 composition is separate and does
not use `hosted_mode` conditionals or redirect the V2 corpus loader.

## Identity And Metadata

`Document` is the logical source record. `DocumentVersion` is one immutable upload. A new
upload for the same document creates a new version number and object identity; it never
overwrites an earlier version.

Object keys have this generated form:

```text
documents/<organization-id>/<workspace-id>/<document-id>/<document-version-id>/source
```

All identifiers are generated by AIRA. The original filename is separate display metadata,
never part of authorization and never used in an object key. A key prefix is useful for
operations but is not a tenant-security boundary.

PostgreSQL stores the category, state, original filename, expected and verified SHA-256,
size and media type, storage provider, opaque key, actor, timestamps, classification,
retention marker, content-safety state, and object-cleanup state. Browser-facing service
results do not return the raw object key.

## Upload And Finalization

The hosted upload flow is:

```text
ActorContext
  -> KNOWLEDGE_MANAGE authorization
  -> active workspace validation
  -> pending Document and immutable DocumentVersion under RLS
  -> short-lived presigned PUT
  -> direct client upload
  -> HEAD with checksum mode
  -> expected/verified metadata comparison
  -> AVAILABLE transition and durable audit
```

The signed PUT requires the exact content length and content type, SHA-256 checksum headers,
`If-None-Match: *`, and SSE-KMS headers. Application finalization does not trust those input
claims: it reads provider-reported size, type, and SHA-256 and compares them with the pending
version. S3 ETag is not treated as SHA-256.

Missing objects leave the version pending so a not-yet-completed upload can be retried.
Checksum, size, or type mismatches transition the version to failed. Failed rows retain the
opaque object identity and a cleanup-required signal. An authorized cleanup operation can
delete that failed object and record `object_deleted_at`. Provider errors do not fabricate a
successful finalization.

Finalization is idempotent after success. Concurrent state transitions use conditional SQL
updates, and the unique `(document_id, version_number)` and object-key constraints reject
conflicting version creation. Database checks require verified metadata to equal expected
metadata for every available version.

## Download And Archive

Downloads require fresh `KNOWLEDGE_READ` authorization and RLS-scoped document/version
ownership checks. Only available versions of an unarchived document receive a short-lived
presigned GET. The issuance is audited without storing the URL, object key, credentials, or
headers.

Archive is a logical PostgreSQL transition. It blocks new versions, finalization, and
downloads but retains immutable available objects. Physical deletion of available objects is
deferred until V3.8/V3.9 define index references and V3.25 defines retention/deletion policy.
This prevents an archive operation from silently breaking a future published index. Failed
upload objects have an explicit cleanup path in V3.7.

## Supported Content And Safety

The initial hosted allowlist mirrors the text-oriented V2 corpus:

- Markdown: `.md`, `.markdown`
- Plain text and logs: `.txt`, `.log`
- YAML: `.yaml`, `.yml`

The application validates a plain filename, exact allowlisted media type, a configurable
positive size no greater than the deployment policy, and a lowercase SHA-256 digest before
issuing an upload. Unknown types fail closed.

V3.7 records `not_scanned` and defines future content-safety states, but it does not execute
malware scanning, DLP, content sanitization, or semantic validation. Successful size/type/
checksum verification means only that storage matches the declared immutable version; it
does not mean the content is safe. Production intake must not claim malware or DLP coverage
until those hooks are implemented and enforced.

## S3 Adapter

`DocumentObjectStorage` exposes only presigned upload/download, stat, and delete operations.
`S3DocumentStorage` receives its client and configuration through composition. Bucket,
region, optional compatible endpoint, KMS key ID, timeouts, and retry bounds are configurable;
credentials come from the normal workload credential chain and are never stored in workspace
configuration or source.

V3.7 creates no bucket, key, role, policy, or AWS resource. V3.22 owns infrastructure,
private-bucket policy, access logging, lifecycle policy, KMS policy, and production orphan
cleanup scheduling.

Unit tests use deterministic in-memory storage and injected fake S3 clients. Real PostgreSQL
tests cover metadata constraints, transaction rollback, missing context, cross-workspace RLS,
and durable audit. No AWS account, LocalStack, moto, or V2 Compose change is required.
